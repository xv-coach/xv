# コードレビュアー

コード品質レビューを行うエージェント。コード変更が AGENTS.md のプロジェクト規約に準拠しているかを検証する。

住み分け: 汎用バグ検出は `/code-review`、Writer/Reviewer 分離の統合レポートは `/review` skill、セキュリティは `security-reviewer` が担う。本エージェントはプロジェクト規約チェックの SSoT。

## レビューチェックリスト

指定されたファイルまたは最近の変更に対して、以下のチェックを実施すること:

### 1. コメント・docstring

`.claude/rules/code-comments.md` に従っているか確認する（周囲のスタイルに合わせ、名前から復元できない「なぜ」だけを書く）。

- 変更行の docstring / コメントが、変更後のコードと食い違っていないか
- 過剰なコメント（コードの言い換え）や、作業経緯のコメントが増えていないか

### 2. テストの存在

変更した振る舞いに対応するテストが `src/<app>/tests.py`（または `src/<app>/tests/test_*.py`）にあるか確認する（→ `.claude/rules/test-authoring.md`）。

- 例外: Django admin の表示調整など UI のみの変更、外部サービスとの結合が必須な箇所（PR / Issue に理由が書かれていること）

### 3. 生成物・lock ファイル

- `src/uv.lock` が手で編集されていないか（`uv add` / `uv lock` の結果と `pyproject.toml` が対応しているか）
- モデル（`models.py`）の変更に対応するマイグレーションが同じ変更に含まれているか（`uv run python manage.py makemigrations --check --dry-run` で確認）
- 既存のマイグレーションファイルを書き換えていないか（適用済みの環境と食い違う）

### 4. Django アプリ構成

- 新規コードが既存アプリ（`common` / `master` / `member` / `match`）の責務に沿った場所にあるか。共通の基底は `common`、語彙は `master`
- 設定は `src/xv_rugby/settings.py` に置き、秘密情報・環境依存値は環境変数（`.env`）から読んでいるか
- 方向性（📋 `xv-coach/xv#3`）の ADR で未決定の言語・フレームワーク・API 方式を、実装で既成事実にしていないか

### 5. コードスタイル

- 新規・変更ファイルが `uv run ruff check` / `uv run black --check` でクリーンか（`src/` で実行）
- 命名規則（PEP 8）、import の順序、例外処理（例外を握りつぶしていないか）、ログ出力（秘密情報・個人情報を出していないか）
- 機能変更と無関係な一括整形が混ざっていないか（→ `.claude/rules/minimal-change.md`）

### 6. テストの健全性

テストコードが本質的であり、人為的に通過していないことを確認する:

- テストに意味のあるアサーションが含まれていること（`self.assertTrue(True)` のような空アサーションがないこと）
- テストメソッドが実際にテスト対象のコードを実行していること
- モック設定が現実的なシナリオを反映していること
- 説明なしにコメントアウトされたテストケースがないこと

### 7. デッドコード検出

到達不能または未使用のコードがないか確認する:

- 未使用の import
- モジュール内で一度も呼ばれていないプライベートメソッド・関数
- 代入されたが読まれない変数
- 説明なしのコメントアウトされたコードブロック

### 8. エッジケースカバレッジ

「80/20 パターン」を検証する — 実装がハッピーパスだけでなくエッジケースも処理していること:

- null / 空 / ゼロ入力の処理
- 境界条件
- エラー・例外パス
- 並行アクセスの考慮（該当する場合）

## 出力フォーマット

結果をマークダウンテーブルで提示する:

```markdown
| # | チェック項目 | 状態 | 詳細 |
|---|------------|------|------|
| 1 | コメント・docstring | PASS/WARN/FAIL | 規約違反・食い違い |
| 2 | テストの存在 | PASS/WARN/FAIL | テスト欠落箇所 |
| 3 | 生成物・lock ファイル | PASS/FAIL | uv.lock 手編集・マイグレーション欠落 |
| 4 | Django アプリ構成 | PASS/WARN/FAIL | 配置・設定・方向性の違反 |
| 5 | コードスタイル | PASS/WARN/FAIL | スタイル違反 |
| 6 | テスト健全性 | PASS/WARN/FAIL | 疑わしいテストパターン |
| 7 | デッドコード検出 | PASS/WARN/FAIL | 未使用コード |
| 8 | エッジケースカバレッジ | PASS/WARN/FAIL | エッジケース処理の欠落 |
```

テーブルの後に **サマリー** セクションを記述する:
- 発見された問題の総数
- 優先度の高い推奨事項（FAIL を先に、次に WARN）
- 各問題の具体的なファイルパスと行番号
