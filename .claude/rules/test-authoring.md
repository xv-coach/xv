# テスト作成規約

コードを変更するときは、対応するユニットテストを作成・更新する。

- **新機能追加時:** 新しいクラス・メソッドに対するテストを作成する
- **バグ修正時:** 修正内容を検証するリグレッションテストを作成する
- **リファクタリング時:** 既存テストが通ることを確認し、必要に応じてテストも更新する
- **テスト配置:** Django アプリでは `src/<app>/tests.py`、増えたら `src/<app>/tests/test_<対象>.py` に分ける（`tests/__init__.py` を置く）。`django.test.TestCase` を使い、`src/` で `uv run python manage.py test [<app>]` で実行する。新しい言語・フレームワークを採用したら、その標準の配置に従う
- **テスト命名:** テスト対象が明確に分かる命名にする（例: クラス `<対象>Tests`、メソッド `test_<振る舞い>`）
- **テストデータ:** 架空の値だけを使う。実在選手の氏名・写真・旧 DB dump・実在のメールアドレスや認証情報は使わない
- **DoD への記載:** Issue の DoD には、実装とセットでテストの作成を含める
- **進め方:** テストを 1 つ書いて失敗を確かめ、通す実装を書いてから次のテストに進む（垂直スライス）。先に全テストを書き切ると、実装で分かった設計の変化にテストが追従できない

**例外:** Django admin の表示調整など UI のみの変更や、外部サービスとの結合が必須で単体テストが困難なクラスは、テスト作成を省略してよい。ただし、その場合は Issue にテスト省略の理由を明記すること。

> 検証可能ゴールへの変換は `testing.md`、コミット前の検証項目は `definition-of-done.md` Phase 3、テストの設計（どの層を叩くか・何を double にするか・assert の書き方）は `test-design` skill を参照。
