# コードコメント規約

**周囲のコードのコメント密度・スタイルに合わせる。** 既存ファイルを編集するときは、そのファイルが実際に採用している水準が基準であり、この規約より優先する。

## コメントが価値を持つ箇所

以下は名前や型からは復元できない情報であり、書く価値が高い。

- **非自明なアルゴリズム・ワークアラウンド** — なぜこの実装なのか（外部ライブラリのバグ回避、パフォーマンス上の制約など）
- **正規表現パターン** — 何にマッチさせる意図か
- **マジックナンバー・定数** — その値である理由
- **名前だけでは責務が読み取れないクラス・モジュール** — 責務を 1〜2 文で

## コメントが価値を持たない箇所

コードを読めば分かることの言い換えは、レビュー時のノイズになり、実装が変わったときに嘘になる。

- シグネチャを日本語に訳しただけの関数コメント
- Getter / Setter、自明な名前のデータクラスプロパティ
- 親の説明で足りるインターフェース実装メソッド
- テスト名が説明的なテストメソッド

## 新規ファイル・公開 API

新規に作るモジュールや、他パッケージから使われる公開 API では、呼び出し側が実装を読まずに使えるだけの説明を置く。パラメータの意味が名前から自明でない場合や、戻り値・例外に規約がある場合は明記する。

## 言語

既存コメントの言語に合わせる。新規ファイルはプロジェクトの方針（`AGENTS.md` に書く）に従う。言語をそろえるためだけに既存コメントを一括で翻訳しない（差分が膨らみ、本来の変更がレビューできなくなる）。

---

> **判断に迷ったら:** そのコメントを消したときに、次にこのコードを読む人が実装の意図を誤解するか。誤解するなら残す。
