# 検証規約

テストの作成義務・配置・命名は `test-authoring.md`、コミット前の検証項目は `definition-of-done.md` Phase 3 を参照。

## 検証可能ゴールへの変換

曖昧な指示は、着手前にテストで表現できる完了条件に変換する。テストで表現できれば「実装 → 実行 → 修正」を自律的に回せるが、「動くようにして」のままでは毎回人間の確認が要る。

| 曖昧な指示 | 検証可能ゴール |
|----------|---------------|
| 「バリデーション追加」 | 不正入力で失敗するテストを作成 → 実装後に通る |
| 「バグ修正」 | バグを再現するリグレッションテストを作成 → 修正後に通る |
| 「リファクタリング」 | 変更前にテストが全件パスすることを確認 → 変更後も同一テストがパス |
| 「パフォーマンス改善」 | ベンチマーク値を測定 → 目標値を上回ることをテストで保証 |
| 「モデル変更」 | `makemigrations --check --dry-run` が差分なし（マイグレーション作成済み）+ テストがパス |
| 「機能 X を追加」 | X の受け入れ条件をテストとして書き、Red → Green を確認 |

複数ステップのタスクは各ステップに検証方法を併記する（例: `1. 得点集計の実装 → 検証: uv run python manage.py test match 全件パス`）。

## 失敗時

検証が失敗したら原因を特定して修正し、すべての検証を再実行する。3 回修正しても解決しない場合はユーザーに報告してアプローチを相談する。
