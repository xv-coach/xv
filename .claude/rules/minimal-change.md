# 最小変更原則

要求を満たす最小のコードを、最小の差分で出す。レビュー負荷を下げ、本質的な変更を見えやすくするため。

- 要求されていない機能・設定可能性・拡張ポイント・起こり得ないケースのエラー処理は書かない。一度しか使わないコードは抽象化しない
- 信頼境界（ユーザー入力・外部 API）では入力を検証する。社内コード間の呼び出しは型と契約を信頼してよい
- 変更は要求に直接紐づく行に限る。隣接コードのリファクタ・フォーマット修正・スタイル変更は混ぜず、既存のスタイルに合わせる
- 自分の変更で不要になった import / 変数 / 関数は消す。元からあったデッドコードは言及にとどめ、明示要求がない限り消さない
- 「ついでに直した」行が混ざったら別コミット / 別 PR に分ける
