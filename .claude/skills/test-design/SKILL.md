# テスト設計ガイド

何を・どの入口から・何を本物のまま検証するかを決め、assert の形を揃えるための骨格。テストを書く義務・配置・命名は `.claude/rules/test-authoring.md` が扱う。書き始める前に、対象コードと同じ層の最も近い既存テストを読んで形を合わせる。

> xv での読み替え: 本 skill と `references/` のコード例は TypeScript（Vitest 風）で書かれているが、考え方は言語に依らない。Django では `django.test.TestCase`（DB を使うテストはトランザクションで自動ロールバック）、`it.each` は `self.subTest`、HTTP の入口は `self.client` / `django.test.Client`、時刻は固定値を引数で渡すか `unittest.mock.patch` で差し替える。テストデータは架空の値だけを使う。将来 ReScript のフロントエンドを書くときは、例をそのまま当てはめやすい。

## 何をテストするか

テストする:

- ビジネスルール（項目間の制約、権限境界、状態遷移）
- 境界値（下記の 3 点）
- 既知のバグ。原因と結び付けておくと後で退役を判断できる
- 公開インターフェースの入出力（ハンドラ、ユースケース、リポジトリ、hook）
- エラー経路を正常系と同じ重みで。入力検証、認証・認可の失敗、一意制約などの競合、外部依存の失敗。最後のものは握りつぶしが隠れやすい

テストしない（仕様を守らず、実装変更で壊れるだけになる）:

- 自前の依存に対する呼び出し回数などの実装詳細
- private ヘルパーの網羅（公開入口から通す）
- 型システムが保証済みのこと、見た目
- 同じルールを複数の層で重ねて検証すること

### 期待値は推測せず確定させる

仕様書・ADR・Issue・`docs/` → バリデーションスキーマの制約（min / max / 正規表現）→ enum / union / nullable の列挙、の順に当たる。それでも決まらなければ書く前にユーザーに確認する。推測した期待値のテストは通っても何も保証しない。

### 境界値は内側・境界・外側の 3 点

中間値 1 つではルールを固定できない。3 点はスキーマが参照する定数から導出する。現在値をコピーすると、上限変更後も古い境界を検証し続けるため。ここでの定数は期待値ではなく制約なので、「期待値はリテラル」の例外になる。

```typescript
it.each([
  ['内側', 'a'.repeat(TITLE_MAX - 1), true],
  ['境界', 'a'.repeat(TITLE_MAX), true],
  ['外側', 'a'.repeat(TITLE_MAX + 1), false],
])('title 境界値 (%s)', (_label, title, ok) => {
  expect(validate({ ...validInput, title }).success).toBe(ok)
})
```

## どの入口から叩くか

各層が実際に持つ入口を 1 つだけ叩く。準備に別の入口が必要なら層を取り違えている。

| 層 | 叩き方 | 本物のまま | assert |
|---|---|---|---|
| スキーマ / 純粋関数 | 直接呼ぶ | - | 戻り値 / エラー |
| ユースケース | 公開メソッド | 自前の DB | 戻り値と永続化された行 |
| リポジトリ実装 | メソッド | DB | 読み戻した行、制約違反の変換結果 |
| HTTP ルート | インプロセス呼び出し | DB・認証 | status・ヘッダ・body 全体 |
| フロントエンド hook | 描画して呼ぶ | - | 状態と外部呼び出し |
| E2E | ブラウザ操作 | すべて | ユーザーに見えるもの |

ブラウザ自体が対象のときだけ E2E を選ぶ。ルートは多くのフレームワークでサーバー起動なしに叩ける。

## テストダブル: 状態は観測し、失敗は注入する

線引きは「自前か他人か」ではなく「状態か失敗か」。

- 自前の DB は本物のリポジトリ実装で使い、戻り値と行を assert する。呼び出し引数の assert は、仕様が同じでも引数が 1 つ増えただけで落ちる
- 呼び出しの assert は、効果がプロセス外に出る外部システム（メール、キュー、ストレージ、外部 HTTP）に使う
- 「書き込まれなかった」は「行が無い」で assert する
- 本物では起こせない失敗（コネクション断など）は reject するダブルで注入し、呼び出し側のラップを assert する

理由、DB の分離方式、DB エラー後の状態、並行性、環境変数は `references/structure.md`。

## assert の要点

- 値全体を `toEqual` に渡す。断片チェックは書き忘れたフィールドの誤りを通す
- 件数は `toHaveLength(2)` のように厳密に。`toBeGreaterThan(0)` や `forEach` 内の assert は間違った行でも通る
- 配列は肯定形で一致させる。`filter` 後に空を assert すると無関係な要素が素通りする
- 文字列は `toBe` で全文。予測不能な部分だけ `expect.stringMatching` / `expect.any(String)`
- エラーは型とメッセージを厳密に。HTTP は status だけでなくエラーコードを含む body まで固定する
- 時刻はフェイクタイマーで固定し、ステップ間の時刻は明示的に設定する
- 期待値の中で計算・関数呼び出しをしない。採番 ID だけは作成結果から取る
- assert する値はセットアップで明示的に与える
- ログは、セキュリティ上の仕様か振る舞いの唯一の痕跡であるときだけ、実出力を捕捉して assert する

NG/OK 例、クラスインスタンスと `toEqual`、タイマーで I/O が止まる件、ログ捕捉は `references/assertions.md`。

## テストの形

- Arrange / Act / Assert を空行で分け、1 テストで 1 仕様を証明する（同じ仕様の複数側面なら複数 assert でよい）
- `describe` は関数名ではなく責務（権限、入力検証など）でまとめる
- フィクスチャは本番と同じバリデーションを通る値にする
- 文字列検索のフィクスチャは `xyzzy` のような衝突しないトークンにする。`test` や `9999` は生成値と衝突する

## リファクタ後にテストが壊れたら

仕様が変わらず落ちたならテスト側の欠陥を先に疑い、当てはまればテストを書き直す。

| 症状 | 直し方 |
|---|---|
| 内部ヘルパーの戻り値や自前依存の呼び出し履歴を検証 | 入口から戻り値と永続化状態を assert |
| private 相当を直接呼ぶ | 公開入口から叩く。無理ならコードに差し込み口を作る |
| 公開 API で再現できない順序・回数を検証 | 行・レスポンス・描画など観測可能な結果を assert |
| スナップショットを毎回丸ごと更新 | 仕様が述べる点だけを assert |

仕様が変わって落ちたなら、期待値を新しい仕様に合わせる。
