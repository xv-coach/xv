# 層・テストダブル・DB 分離

`SKILL.md` の「どの入口から叩くか」「テストダブル」の背景。

## 自前の DB を本物で使う理由

ユースケースのテストで自前のリポジトリをダブルにすると、検証が薄くなるだけでなく実装に固定される。

```typescript
// NG: ユースケースが引数を 1 つ多く渡し始めると、仕様が同じでも落ちる
expect(repo.create).toHaveBeenCalledWith({ title: 'Buy milk', ownerId: 'user-1' })

// OK: 行が正しい限り通り続け、行が誤れば落ちる
const created = await usecase.create({ title: 'Buy milk' }, { userId: 'user-1' })
expect(created).toEqual({ id: created.id, title: 'Buy milk', ownerId: 'user-1' })
expect(await db.select().from(tasks)).toEqual([
  { id: created.id, title: 'Buy milk', ownerId: 'user-1' },
])
```

「リポジトリが書き込みを依頼されなかった」は実装の記述で、「行が存在しない」は仕様の記述になる。後者で assert する。

ダブルに置き換えるもの:

| 依存 | 扱い |
|---|---|
| メール・キュー・ストレージ・外部 HTTP | ダブルにして呼び出しを assert する（効果がプロセス外に出るので、呼び出しが観測対象そのもの） |
| フロントエンドテストの `fetch` | ダブル。hook のテストにサーバーは無い |
| 画面コンポーネントのテストで使う状態 hook | ダブル。hook 自身のロジックは hook のテストで検証する |
| 時計 | フェイクタイマー（`assertions.md` の「時刻を固定する」） |
| 自前のリポジトリ | 失敗注入のときだけ。`mockRejectedValue(new Error('connection lost'))` のように差し込み、呼び出し側がどうラップするかを assert する |

## どの DB で走らせるか

| 状況 | 実行基盤 |
|---|---|
| 永続化された状態が仕様に含まれる（ユースケース、リポジトリ、ルート） | 本番と同じ DB エンジン |
| 一意制約・外部キー・NOT NULL 違反がドメインエラーに変換されること | 本番と同じ DB エンジン |
| ロック、行レベルセキュリティ、拡張、マイグレーション互換 | 本番と同じ DB エンジン |
| スキーマ定義と基本 CRUD の高速な疎通 | 組み込み / インメモリの互換 DB でもよい |
| 純粋関数、スキーマ、整形、フロントエンド | DB 不要 |

組み込み・インメモリの互換 DB は大半の SQL で同じ結果を返すが、エラーコードやロックの細部は本番と一致しないことがある。本番の挙動そのものが検証対象なら本番と同じエンジンを使う。

## テストごとのトランザクション・ロールバック

スタックが対応していれば、ワーカーごとに DB を分け、各テストを 1 つのトランザクションで包んで最後にロールバックする方式が扱いやすい。本番コードの DB ハンドルをテスト中のトランザクションへ差し向ける仕組み（DI、プロキシ、フレームワークのテスト用フィクスチャなど）が必要になる。Python なら pytest フィクスチャでトランザクションを開き、セッションをそれに束縛する形がよく使われる。

この方式で得られるもの:

- 固定のリテラル ID やメールアドレスをそのまま使える。DB に他のデータが無いため
- 件数を厳密に assert できる（`toHaveLength(2)`）
- 後片付けが要らない。ロールバックが片付けになる。テスト途中の手書き DELETE は外部キー違反の原因になる
- フィクスチャは `beforeEach` かテストスコープのフィクスチャで作る。`beforeAll` やファイル・ワーカースコープのフィクスチャはトランザクションの外でコミットされ、次のテストに漏れる

テストの外で走った書き込み（await されない fire-and-forget など）は実 DB にコミットされてロールバックを逃れる。テスト前後で行数を比較して検出する仕組みがあれば、その失敗は「不安定」ではなく「書き込みがトランザクションを逃れた」と読む。

対応していないスタックでは、テストごとに一意なデータ（接頭辞付き ID など）を使い、件数は自分が作った範囲に絞って assert するか、スイートごとに TRUNCATE する。

### DB エラーの後は同じテストで状態を assert できない

PostgreSQL などは、トランザクション内で文が失敗するとそのトランザクションを中断状態にし、以降の文をロールバックまで拒否する（PostgreSQL では SQLSTATE `25P02`）。テスト全体が 1 トランザクションなので、制約違反の後の SELECT は期待値ではなく SELECT 自体で落ちる。

```typescript
// NG: 2 つ目の文が 25P02 で落ちる
await expect(repo.create({ receiverId: 'no-such-user' })).rejects.toThrow(ForeignKeyError)
expect(await db.select().from(messages)).toEqual([])

// OK: エラーだけを assert して終える
await expect(repo.create({ receiverId: 'no-such-user' })).rejects.toThrow(ForeignKeyError)
```

これは「戻り値と行の両方を assert する」の例外になる。制約違反を起こした文はそもそも何も書き込まないので、「行が無い」は情報を足さない。状態の assert を別テストに分けても同じ文で中断するので解決しない。try/catch で JavaScript の例外を捕まえても DB 側の中断は解けない。

対象コード自体が失敗後も処理を続ける仕様（リトライ、フォールバック、冪等な upsert）なら、コード側でネストしたトランザクション（SAVEPOINT）を使っているはずで、SAVEPOINT までロールバックすれば外側のトランザクションは続行できる。その場合は後続の状態も assert できる。後続の SELECT を通すためだけにテスト内でトランザクションを足すことはしない。

### 本番コードのトランザクションは SAVEPOINT になる

多くの ORM は、既に開いたトランザクションの中で開始されたトランザクションを SAVEPOINT として発行する。本番コードが開くトランザクションはテストのトランザクションの内側にネストし、何もコミットされない。「内側がロールバックされたので何も残らない」という assert は成り立つが、トランザクション ID や統計ビューに対する assert は成り立たない。

### このモデルで再現できないもの

全テストが 1 接続・1 トランザクションで走るので:

- セッション間の競合は起きない。同じ一意キーへの 2 つの INSERT は直列に実行される
- `SELECT ... FOR UPDATE` はブロックしない。テスト自身が既にロックを保持している
- `Promise.all([a, b])` は並行実行にならない。同じ接続に順に積まれる

代わりに、もう一方の呼び出し元が残したはずの状態（期限付きのロック行、処理済みの受信記録など）を先に挿入してから対象コードを呼ぶ。本当の並行性でしか現れない振る舞いは、このモデルの外（複数接続を張る結合テストなど）で検証し、そのことをテストに書いておく。

## 環境変数に依存するコード

どちらの手段が要るかは、対象コードが環境変数を読むタイミングで決まる。

- 実行時に読む（関数内で設定読み込みを呼ぶ）: 環境変数をスタブし、設定のメモ化キャッシュがあればクリアする。静的 import のままでよい
- import 時にモジュールスコープで読み込み済み: 既に作られたインスタンスは変わらないので、モジュールレジストリをリセットして対象モジュールだけを動的 import し直す。バレルごと再 import すると DB 接続などが二重に作られるので、対象を絞る

```typescript
vi.stubEnv('LOG_LEVEL', 'warn')
vi.resetModules()
const { logger } = await import('./logger')
```

Python では `monkeypatch.setenv` の後、import 時に読むモジュールだけ `importlib.reload` する。

新しいコードでは、設定を引数で受け取る（`createLogger(config)`）か関数内で読むようにすると、1 つ目の手段だけでテストできる。import はファイル先頭に静的に書き、動的 import は上記のように import 時の値を作り直す必要があるモジュールに限る。
