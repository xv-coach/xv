# ADR 0001: バックエンド言語と API 方式の評価方法

- **Status: Proposed**
- 日付: 2026-10-26
- 関連: 📋 `xv-coach/xv#3`（方向性の集約先）、[`docs/cms/`](../cms/README.md)（P0 の契約・受入仕様・fixture）

> この ADR は**何も採用しない**。候補、同一条件で比較する項目、未決事項、次の判断ゲートだけを記録する。
> Accepted になるまで、特定の言語・フレームワーク・API 方式・DB 形式・既存 CMS の採用を、実装や設定で既成事実にしない（`AGENTS.md`、`.claude/rules/definition-of-done.md`）。

## 背景

xv は、複数のラグビークラブが選手・ニュース・試合結果を管理する**ヘッドレス CMS** を目指す。初期構成は、モジュール境界のある単一サービスを基本案とし、最初からマイクロサービス化しない。現在の `src/` は Django の管理画面だけのレガシー実装（Python 3.14 / Django 6.1 / PostgreSQL 18 に更新済み。詳細は [`docs/cms/README.md`](../cms/README.md)）で、公開 API・公開サイトは無い。

比較の共通入力は、P0 で定めた選手紹介 1 フローの契約（[`player-profile-contract.md`](../cms/player-profile-contract.md)）、受入仕様（[`player-profile-acceptance.md`](../cms/player-profile-acceptance.md)）、架空 fixture（[`player-profile-scenarios.json`](../cms/fixtures/player-profile-scenarios.json)）とする。

## オーナーの方針・意向（2026-10-26 時点）

以下はリポジトリ管理者が示した方針と意向。バックエンド言語・API 方式については**比較の重み付けに使う入力であり、採用決定ではない**。管理 UI の方針（下の 1〜4）は、**Django を選んだ場合の前提・制約**としてオーナーが方向性を決めたもの。

### リポジトリの分担

- 将来、**公開サイト（エンドユーザー向け。ReScript を優先）だけを別リポジトリ**に置く。管理画面は本リポジトリに残し、`xv-coach/xv` は**バックエンド**（管理画面・コンテンツ管理・API）を担う
- その結果、**API 契約がリポジトリ間の境界**になる。契約の版管理・互換性の方針、公開サイト側リポジトリが契約を取り込み・デコード・検証する方法（スキーマからの生成か手書きのデコーダか、共有 fixture による契約テストか）が、言語・API 方式の比較で重要になる
- 公開 DTO の許可リストの変更は、契約の版を上げる変更として扱う（互換性の規則は未決）

### 管理 UI の方針（Django を選んだ場合）

オーナーが Django 標準 admin を魅力的と考えていることは、**Python / Django 寄りに働く考慮事項**（管理画面・認証・ORM を再利用できる）として記録する。ただし 📋 `xv-coach/xv#3` は G2〜G4 の比較を経て決めることを求めており、この方針だけで Django を採用しない。他の言語を選ぶ場合は、管理 UI を別途用意する費用を比較に含める。

1. **管理画面は本リポジトリに置く。** 別リポジトリへ移すのは公開サイトだけ。Django admin 全体を ReScript で書き直すことは**計画しない**。認証・権限・フォーム・入力検証・一覧の絞り込み・CSRF 対策・変更履歴を作り直すことになり、得るものが少ないため
2. **見た目は自前のテンプレート・CSS で改善する。** チームが AI エージェントの支援を受けて書き、第三者の admin テーマ（例: django-unfold）は使わない（外部テーマの保守に依存しないため。AI エージェントで自前テンプレートの負担が下がると見込むため。後者は推定で、G2 で確かめる）。版更新時の摩擦を抑えるため、上書きは **土台のテンプレート（`admin/base_site.html` など）と CSS に限る**
3. **通常のフォームで扱えない画面はプラグインとして追加する。** 例: ブロック単位の本文編集、メンバー表のドラッグ＆ドロップ、試合中のスコア入力、公開時の見た目でのプレビュー
   - 1 プラグイン = 1 Django アプリ（`INSTALLED_APPS` に登録）。Python 側のビュー・権限・URL（独自の `AdminSite` サブクラスの `get_urls()`、または `ModelAdmin.get_urls()` で登録）と、ReScript からコンパイルした JS / CSS（Django の `Media` の仕組みで宣言）をまとめる
   - 独自の `AdminSite` が、登録されたプラグインをナビゲーションに表示する
   - フォームのウィジェットとして埋め込む形も認める
   - サーバーからのデータ受け渡しは `json_script` を使う。インラインスクリプトは書かない（CSP に対応しやすくするため。Django は CSP を扱う仕組みを持つ）
4. **jQuery を使わない。** 導入済みの Django 6.1 で次を確認した
   - `ModelAdmin.media` は常に `vendor/jquery` と `jquery.init.js` を読み込む（`InlineModelAdmin.media` も同様）
   - jQuery に依存する admin の JS は `inlines.js`、`admin/RelatedObjectLookups.js`、`autocomplete.js`（select2）、`prepopulate.js` / `prepopulate_init.js` だけ。それ以外（`actions.js`、`calendar.js`、`admin/DateTimeShortcuts.js`、`nav_sidebar.js`、`theme.js`、`filters.js`、`SelectFilter2.js` など）は jQuery を使わない
   - 方針: xv 共通の基底 `ModelAdmin` / `InlineModelAdmin` で `media` を上書きして jQuery を外し、上の依存ファイルを ReScript からコンパイルした同等品に置き換える。`select2` / `autocomplete_fields` の代わりに ReScript の自動補完ウィジェットを使う。プラグインも同じ基底を使う。admin の HTML に jQuery が含まれないことをテストで確かめる
   - 費用: 置き換えた JS は Django admin の**非公開の DOM 構造**に依存する。そのため、インラインの追加・削除、関連オブジェクトのポップアップ、自動補完をブラウザの E2E テスト（例: Playwright）で確かめ、Django の版を上げるたびに再実行する。jQuery を前提とする第三者の admin 拡張は使えなくなる

📋 `xv-coach/xv#3` の P2 にあった「ReScript を優先した最小の管理 UI」は、この方針に合わせて解釈する。ReScript は**別リポジトリの公開サイト**と、**管理画面の複雑な画面（プラグイン）**に使い、管理画面の土台は自前デザインの jQuery を使わない Django admin とする（Django を選んだ場合。G2〜G4 の判断が前提）。

## 候補

| 候補 | 評価の仮説（未検証） |
|---|---|
| **Go** | 独自 CMS を新規に作る場合のバランス重視の有力候補。標準ライブラリと並行処理。管理画面・認証・権限をどこまで自作するかの見積もりが必要 |
| **Rust** | 実行効率と型・メモリ安全性。コンパイル時間、ビルド生成物の容量、実装・運用の複雑さとの釣り合いを検証する |
| **Haskell** | ドメインや不正な状態を型で表す。Servant などが候補。依存ライブラリ、専門性、運用知識、遅延評価に伴うメモリ挙動を確認する |
| **Python / Django** | 認証・ORM・管理画面が成熟。旧モデルを参照した再設計につながる。**オーナーの admin 再利用の意向がこの候補に有利に働く。** CPU 負荷・同時実行性はキャッシュ・ワーカー構成を含めて実測する |
| **ReScript / Node.js** | フロントエンドと知識を共通化できる。JavaScript ランタイム上なので、型の利点と実行性能を分けて評価する。FFI、外部データの検証、非同期処理の設計を確認する |

全候補で CMS を並行実装する必要はない。理由なく 1 言語へ進まない。

## API 方式

ヘッドレス構成に GraphQL は必須ではない。REST と GraphQL の両方を候補に残す。

- **REST:** 単純さ、HTTP キャッシュ・CDN の扱いやすさ。一覧・詳細の取得パターンが少ないうちは有利かもしれない（推定）
- **GraphQL:** 選手・チーム・試合の関係をフロントエンド側で柔軟に取得できる。採用する場合はページネーション、クエリ深度・コストの制限、N+1 対策、フィールド・テナント単位の認可、公開キャッシュの方法が必要。Go を選ぶ場合の実装候補に gqlgen があるが、いずれも未決
- 「ヘッドレスである」ことだけを採用理由にしない

### 管理 UI の比較項目（Django admin の自前デザイン改善・プラグイン・jQuery 除去）

Python / Django を候補に残す場合に確かめる（上の「管理 UI の方針」1〜4 が前提）。

| 項目 | 確かめ方 |
|---|---|
| テンプレート上書きの範囲 | 土台のテンプレート（`admin/base_site.html` など）と CSS の上書きだけで、狙った見た目になるか。上書きする量 |
| Django の版更新時の摩擦 | 上書きしたテンプレートが Django のメジャー / マイナー更新で壊れる頻度と修正量（過去の版間差分で見積もる。推定と実測を分ける） |
| アクセシビリティ | キーボード操作、コントラスト、スクリーンリーダーでの読み上げ。標準 admin より悪くしない |
| admin 画面のテスト | 上書き後も admin のビュー（一覧・編集・権限による表示制御）のテストを持ち続ける方法（既存の `src/tests/test_admin.py` の延長） |
| テナント分離 | admin で他クラブのデータが一覧・検索・選択肢・関連フィールドに出ないこと（受入仕様の他クラブ系シナリオを admin でも確かめる） |
| 公開状態の操作 | 下書き・プレビュー・公開・公開停止を admin の操作として表せるか |
| jQuery の除去 | 基底 `ModelAdmin` / `InlineModelAdmin` の `media` 上書きで jQuery を外せるか。admin の HTML に jQuery が含まれないことを確かめるテストを書けるか |
| 置き換え JS の費用 | `inlines.js`、`RelatedObjectLookups.js`、自動補完、`prepopulate.js` の ReScript 版を作る量と、非公開の DOM 構造への依存の度合い |
| ブラウザ E2E | インラインの追加・削除、関連オブジェクトのポップアップ、自動補完を Playwright などで確かめる手間と、Django の版更新時の再実行 |
| プラグインの仕組み | 独自 `AdminSite` の `get_urls()` / `ModelAdmin.get_urls()` と `Media` で、1 プラグイン = 1 Django アプリを登録・表示できるか。権限の掛け方 |
| CSP | `json_script` によるデータ受け渡しとインラインスクリプト無しで、admin とプラグインが CSP の下で動くか |
| 第三者の admin 拡張 | jQuery 前提の拡張が使えなくなることの影響（代わりに必要になる機能の有無） |
| 第三者テーマとの比較（参考） | 使わない方針。比較の参考として django-unfold などの保守状況・依存を判断時に確認し、自前を選ぶ理由（外部テーマの保守に依存しない）が成り立つかを記録する |

## 未決事項

1. どの候補で短い検証を行うか、その環境（G2 で合意）
2. 実測の条件（データ量、アクセスパターン、DB、キャッシュ）。性能の数値は条件を決めた負荷試験の後に判断する
3. API 契約の記述形式（OpenAPI、GraphQL スキーマ、言語非依存の JSON Schema など）と、別リポジトリの公開サイトでの取り込み方法
4. 契約の版管理と互換性の規則（追加は互換、削除・意味の変更は非互換、など）
5. DB 形式と、旧 Django モデル・migration を引き継ぐかどうか
6. Django 以外を選んだ場合の管理 UI の用意の仕方（📋 `xv-coach/xv#3` の P2 は、Django を選んだ場合について上の「管理 UI の方針」で整理済み）
7. P0 契約の未決事項（[`player-profile-contract.md`](../cms/player-profile-contract.md) §8）

## 次の判断ゲート

📋 `xv-coach/xv#3` の G1〜G4 に従う。

- **G1: slice 合意** — P0 のデータ境界・公開フィールド・権限・受入仕様をレビューする。保留項目は 📋 `xv-coach/xv#3` に集約する
- **G2: 採用候補の絞り込み** — 上の言語の比較項目と管理 UI の比較項目を、同じプロフィール操作で埋める。実測値と推定を混ぜない。サポート中の版と依存をその時点で確認し、短い検証を行う候補と環境を合意する
- **G3: API 判断** — 上の API 方式の比較項目を埋める。GraphQL はクエリコスト・N+1 対策も含める
- **G4: 実装着手可否** — 選定理由と見送った理由、未解決事項、最初の安全な実行・テスト方法がこの ADR に残ったら、Status を Accepted にして backend slice（P1）へ進む。判断が未了なら固定せず、判断材料と残る選択を 📋 `xv-coach/xv#3` に返す

## 影響

- この ADR が Accepted になるまで、`src/` の Django 実装は語彙・関係・制約を知る資料として扱い、新しい選手紹介の機能を実装しない
- Django admin の自前デザイン改善・プラグイン・jQuery の除去に着手する場合も、Django 採用の既成事実にならないよう、範囲と順序を 📋 `xv-coach/xv#3` で確認してから進める
